# Задача BE-3: Автоматическое тестирование (Unit, Integration, WebSocket), унификация ошибок, документация API и CI

* **Приоритет:** Средний
* **Тип:** Testing / Documentation / CI
* **Проект:** Серверная часть многопользовательской карточной игры «Нечто» (Telegram Mini App)
* **Стек и сборка:** Java, Maven (`mvn clean test` / `mvn clean verify`)
* **Связь с задачами:** Завершает подготовку функционала задач `BE-1` (API комнат, лобби и WebSocket) и `BE-2` (СУБД, валидация, транзакции и Docker Compose) к прямой интеграции с фронтендом.

---

## 1. Контекст и цель задачи

Необходимо подготовить backend к полноценной интеграции с клиентским приложением (Frontend):
1. Покрыть **максимальным количеством автоматических тестов** (Unit, HTTP Integration, Concurrency, WebSocket) все позитивные, негативные и граничные сценарии работы игровых комнат и лобби.
2. Снабдить **каждый тестовый метод подробным JavaDoc-комментарием**, описывающим цель теста, входные данные и ожидаемый результат.
3. Унифицировать все ответы об ошибках API через единый глобальный обработчик исключений (`@RestControllerAdvice` / Global Exception Handler).
4. Подробно задокументировать контракт REST API и WebSocket-событий в `OpenAPI (Swagger)` и `README.md`, чтобы фронтенд-разработчик мог подключиться к серверу без изучения исходного Java-кода.
5. Настроить запуск всех тестов одной стандартной командой Maven и автоматическую сборку/прогон тестов в **GitHub Actions CI**.

## 2. Обязательное требование к оформлению тестов (JavaDoc для каждого теста)

**КРИТИЧЕСКОЕ ПРАВИЛО ДЛЯ ИИ-АГЕНТА:**
Над **каждым без исключения** тестовым методом (`@Test`, `@ParameterizedTest`, `@RepeatedTest`) во всех тестовых классах должен быть написан подробный **JavaDoc-блок** (`/** ... */`), объясняющий:
1. **Что проверяет тест** (бизнес-правило или технический сценарий).
2. **Предусловия (Given):** начальное состояние системы/базы данных и входные параметры.
3. **Действие (When):** вызываемый метод сервиса, HTTP-запрос или WebSocket-событие.
4. **Ожидаемый результат (Then):** возвращаемый статус, изменения в БД, выбрасываемое исключение или отправляемое WebSocket-уведомление.

### Пример обязательного оформления тестового метода:

```java
/**
 * Проверяет отказ в подключении нового игрока к комнате, в которой уже достигнут
 * максимальный лимит участников (ROOM_FULL).
 *
 * <p><b>Предусловия (Given):</b> В базе данных существует активная комната в статусе
 * {@code LOBBY} с кодом {@code "FULL04"} и лимитом {@code maxPlayers = 4}, в которой
 * уже зарегистрированы 4 участника.</p>
 *
 * <p><b>Действие (When):</b> Пятый (новый) игрок с {@code telegramId = "555555"}
 * отправляет запрос {@code POST /api/v1/rooms/FULL04/join}.</p>
 *
 * <p><b>Ожидаемый результат (Then):</b>
 * <ul>
 *   <li>Сервер возвращает HTTP-статус {@code 409 Conflict}.</li>
 *   <li>В теле ответа возвращается единая структура ошибки с кодом {@code "ROOM_FULL"}
 *       и понятным сообщением {@code "Комната заполнена"}.</li>
 *   <li>Количество участников комнаты в БД остаётся равным 4 (состояние не изменилось).</li>
 *   <li>WebSocket-событие {@code room:player_joined} не рассылается.</li>
 * </ul>
 * </p>
 */
@Test
@DisplayName("POST /join — Отказ 409 ROOM_FULL при попытке входа 5-го игрока в комнату на 4 человека")
void shouldReturn409RoomFullWhenJoiningFullRoom() throws Exception {
    // реализация теста...
}
```

## 3. Матрица тестирования (Максимальное покрытие сценариев)

ИИ-агент должен реализовать **максимальное количество тестов**, разделив их на логические тестовые классы. Для граничных значений необходимо активно использовать `@ParameterizedTest` (`@ValueSource`, `@CsvSource`, `@MethodSource`).

### 3.1. Модульные (Unit) тесты бизнес-логики (`*ServiceTest`, `*ValidatorTest`, `*GeneratorTest`)
Запускаются быстро с использованием Mockito (`@ExtendWith(MockitoExtension.class)`), без поднятия контекста Spring и БД:

1. **Генерация кода комнаты (`RoomCodeGeneratorTest`):**
   * Генерация кода заданной длины только из допустимых символов (`A-Z`, `0-9`).
   * Повторная генерация кода при коллизии (если сгенерированный код уже существует в репозитории).
   * Успешное формирование корректной `inviteLink` с кодом комнаты.
2. **Создание комнаты (`RoomServiceCreateTest`):**
   * Успешное создание комнаты при всех допустимых значениях `maxPlayers` от $4$ до $12$ включительно (`@ParameterizedTest` для значений $4, 5, 6, 7, 8, 9, 10, 11, 12$).
   * Проверка, что создатель автоматически добавляется в список `players` первым участником с флагами `isCreator = true`, `connectionStatus = ONLINE`, а статус комнаты устанавливается в `LOBBY` и `isReadyToStart = false`.
   * Граничные значения имени комнаты: успешное создание при длине $1$ символ и $32$ символа; корректная обрезка пробелов по краям (`trim()`).
   * Ошибка валидации при `maxPlayers < 4` (значения $-1, 0, 1, 2, 3$) и `maxPlayers > 12` (значения $13, 14, 100$).
   * Ошибка валидации при пустом имени комнаты (`""`, `"   "`, `null`) или длине $> 32$ символов ($33, 50, 255$ символов).
   * Ошибка валидации при некорректном имени создателя (`displayName` пустой или $> 64$ символов).
   * Отказ в создании комнаты (`409 Conflict` / `ACTIVE_ROOM_ALREADY_EXISTS`), если пользователь уже является создателем другой активной комнаты.
3. **Получение информации о комнате (`RoomServiceGetTest`):**
   * Успешное получение комнаты по существующему коду в верхнем регистре (`"X7K9M2"`).
   * Регистронезависимый поиск: успешное получение комнаты при передаче кода в нижнем или смешанном регистре с пробелами (`" x7k9m2 "`).
   * Выброс исключения `RoomNotFoundException` (`404`) при поиске несуществующего кода.
   * Выброс исключения `400 Bad Request` при передаче кода с недопустимыми спецсимволами (`"X7K-9M!"`, `"DROP TABLE"`).
4. **Подключение к комнате (`RoomServiceJoinTest`):**
   * Успешное подключение $2$-го, $3$-го и $4$-го игрока; проверка, что при $3$ игроках `isReadyToStart == false`, а при входе $4$-го игрока `isReadyToStart` автоматически становится `true`.
   * Успешное заполнение комнаты вплоть до $12$ участников (при `maxPlayers = 12`).
   * **Идемпотентное повторное подключение (Reconnection):**
     * Если игрок (обычный участник или создатель), уже находящийся в комнате со статусом `ONLINE` или `DISCONNECTED`, повторно вызывает `join`, дубликат в списке `players` **не создаётся**, его `connectionStatus` переключается в `ONLINE`, `disconnectedAt` сбрасывается в `null`, а `joinedAt` и `isCreator` сохраняют исходные значения.
     * Повторное подключение уже зарегистрированного в комнате игрока разрешено даже тогда, когда комната полностью заполнена (`players.size() == maxPlayers`).
   * **Негативные сценарии подключения:**
     * Отказ `404 ROOM_NOT_FOUND` при подключении по несуществующему коду.
     * Отказ `409 ROOM_FULL` при попытке подключения нового игрока, когда `players.size() == maxPlayers` (проверить для лимитов $4$, $8$, $12$).
     * Отказ `409 ROOM_ALREADY_STARTED` при попытке подключения нового игрока к комнате в статусе `IN_PROGRESS`, `FINISHED` или `ARCHIVED`.
     * Отказ `400 INVALID_PLAYER_NAME` при пустом или содержащем XSS/HTML-теги имени игрока (`"<script>alert(1)</script>"`).
5. **Выход из комнаты и передача прав создателя (`RoomServiceLeaveTest`):**
   * Выход обычного игрока уменьшает `currentPlayersCount`; если игроков стало меньше $4$ (например, было $4$, стало $3$), флаг `isReadyToStart` автоматически сбрасывается в `false`.
   * **Миграция хоста (Host Migration):** при выходе создателя (`isCreator = true`) права создателя (`creatorId` в комнате и `isCreator = true` у участника) автоматически переходят участнику с самым ранним временем входа (`joinedAt`).
   * При выходе последнего оставшегося игрока из комнаты в статусе `LOBBY` комната автоматически удаляется/архивируется.
6. **Изменение настроек комнаты (`RoomServiceSettingsTest`):**
   * Успешное изменение `maxPlayers` создателем комнаты в статусе `LOBBY`.
   * Отказ `403 FORBIDDEN_NOT_CREATOR`, если настройки пытается изменить обычный участник (не создатель).
   * Отказ `400 INVALID_MAX_PLAYERS`, если создатель пытается уменьшить `maxPlayers` ниже текущего количества уже подключённых к комнате игроков (например, в комнате $6$ человек, а создатель ставит `maxPlayers = 5`).
   * Отказ `409 ROOM_ALREADY_STARTED`, если создатель пытается изменить настройки после старта партии (`status != LOBBY`).

### 3.2. Интеграционные тесты HTTP API, БД и конкурентности (`*ControllerIntegrationTest`, `*ConcurrencyIntegrationTest`)
Запускаются в полном контексте (`@SpringBootTest`, `MockMvc` / `TestRestTemplate` и реальная СУБД PostgreSQL через Testcontainers или тестовый профиль):

1. **Полный жизненный цикл через HTTP (`RoomControllerIntegrationTest`):**
   * Проверка всех эндпоинтов (`POST /api/v1/rooms`, `GET /api/v1/rooms/{code}`, `POST /api/v1/rooms/{code}/join`, `POST /api/v1/rooms/{code}/leave`, `PATCH /api/v1/rooms/{code}/settings`).
   * Проверка HTTP-заголовков, `Content-Type: application/json`, структуры JSON-ответов и точного соответствия полей контракту.
   * Проверка идемпотентности и сохранения данных в БД между запросами.
   * Проверка всех кодов ошибок (`400`, `401`, `403`, `404`, `409`, `500`) и того, что при невалидном запросе состояние записей в таблицах `rooms` и `room_participants` остаётся неизменным.
   * Проверка безопасности ошибок: при искусственном вызове ошибки БД в HTTP-ответе клиенту не возвращаются названия таблиц, SQL-запросы или Java stacktrace.
2. **Многопоточные тесты на состояние гонки (`RoomConcurrencyIntegrationTest`):**
   * **Гонка за последнее место в комнате:** в комнате с `maxPlayers = 4` находятся $3$ игрока; через `ExecutorService` и `CountDownLatch` одновременно стартуют $10$ параллельных HTTP-запросов `POST /join` от $10$ разных игроков. Тест проверяет, что ровно $1$ поток получил `200 OK`, ровно $9$ потоков получили `409 Conflict (ROOM_FULL)`, а в таблице `room_participants` итоговое число игроков строго равно $4$.
   * **Параллельное дублирующее подключение одного и того же игрока:** один и тот же игрок отправляет $5$ одновременных запросов `POST /join` в одну комнату. Тест проверяет, что в БД создалась ровно $1$ запись участника без нарушения уникальности и без `500 Internal Server Error`.

### 3.3. Интеграционные тесты WebSocket (`RoomWebSocketIntegrationTest`)
Поднимают сервер на случайном порту (`@SpringBootTest(webEnvironment = RANDOM_PORT)`) и подключаются реальным WebSocket-клиентом:

1. Получение начального события `room:state_sync` сразу после установки WebSocket-соединения с комнатой.
2. Мгновенное получение события `room:player_joined` первым игроком (хостом), когда второй игрок подключается к комнате через REST `POST /api/v1/rooms/{code}/join`.
3. Получение событий `room:player_left` и `room:host_changed` всеми участниками комнаты при выходе создателя.
4. Получение события `room:settings_updated` при изменении `maxPlayers` создателем.
5. Получение события `room:player_connection_changed` (`DISCONNECTED` / `ONLINE`) при закрытии и повторном открытии WebSocket-сессии участником.

## 4. Унификация формата ответов об ошибках

Все ошибки API должны проходить через единый глобальный перехватчик (`@RestControllerAdvice`) и возвращаться в строго фиксированном JSON-формате:

```json
{
  "timestamp": "2026-10-29T12:15:30.123Z",
  "status": 409,
  "path": "/api/v1/rooms/X7K9M2/join",
  "error": {
    "code": "ROOM_FULL",
    "message": "Комната заполнена",
    "details": []
  }
}
```

Для ошибок валидации полей (`400 Bad Request` / `MethodArgumentNotValidException` / `ConstraintViolationException`) массив `details` должен содержать список конкретных полей с ошибками:

```json
{
  "timestamp": "2026-10-29T12:16:00.000Z",
  "status": 400,
  "path": "/api/v1/rooms",
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Ошибка валидации входных параметров",
    "details": [
      {
        "field": "maxPlayers",
        "issue": "Количество участников должно быть в диапазоне от 4 до 12"
      },
      {
        "field": "name",
        "issue": "Название комнаты должно содержать от 1 до 32 символов"
      }
    ]
  }
}
```

### Таблица стандартных кодов ошибок API:

| HTTP Статус | Код ошибки (`error.code`) | Когда возвращается |
| :--- | :--- | :--- |
| `400 Bad Request` | `VALIDATION_ERROR` | Нарушение ограничений полей DTO (`name`, `maxPlayers`, `displayName`) |
| `400 Bad Request` | `INVALID_ROOM_CODE` | Формат кода комнаты не соответствует шаблону `^[A-Z0-9]{4,12}$` |
| `400 Bad Request` | `INVALID_PLAYER_NAME` | Имя игрока пустое, длиннее 64 символов или содержит запрещённые теги |
| `400 Bad Request` | `INVALID_MAX_PLAYERS` | Попытка установить `maxPlayers` меньше текущего числа игроков в комнате |
| `401 Unauthorized` | `UNAUTHORIZED` | Не переданы или невалидны идентификационные данные пользователя Telegram |
| `403 Forbidden` | `FORBIDDEN_NOT_CREATOR` | Попытка изменить настройки комнаты пользователем, не являющимся создателем |
| `404 Not Found` | `ROOM_NOT_FOUND` | Комната с указанным кодом не существует или была удалена |
| `409 Conflict` | `ROOM_FULL` | В комнате уже достигнуто максимальное число игроков (`maxPlayers`) |
| `409 Conflict` | `ROOM_ALREADY_STARTED` | Попытка войти в комнату или изменить настройки, когда статус не `LOBBY` |
| `409 Conflict` | `ACTIVE_ROOM_ALREADY_EXISTS` | Пользователь пытается создать вторую активную комнату |
| `500 Internal Server Error` | `INTERNAL_SERVER_ERROR` | Любая непредвиденная ошибка сервера (без утечки SQL и стектрейсов) |

## 5. Документация API (OpenAPI / Swagger и README.md)

Документация должна быть настолько полной и наглядной, чтобы Frontend-разработчик мог интегрировать клиент без чтения серверного кода.

1. **Автогенерация OpenAPI 3.0 / Swagger UI (`springdoc-openapi`):**
   * Доступность интерактивного Swagger UI по адресу `/swagger-ui.html` (или `/swagger-ui/index.html`) и JSON/YAML спецификации по адресу `/v3/api-docs`.
   * Все контроллеры и DTO должны быть размечены аннотациями `@Tag`, `@Operation`, `@ApiResponses`, `@Schema(description = "...", example = "...")`.
2. **Подробная документация в `README.md` (или отдельном `docs/API.md`, подключённом в `README.md`):**
   * Инструкция по быстрому запуску окружения через `docker compose up --build` и запуску тестов через `mvn clean test`.
   * Описание заголовков аутентификации пользователя (например, передача Telegram `initData` или `X-Telegram-Id`, `X-Player-Name` в dev-режиме).
   * Полное описание каждого HTTP-эндпоинта: метод, URL, параметры пути, схема тела запроса, пример успешного ответа (`200`/`201`) и все возможные ответы с ошибками (`400`/`403`/`404`/`409`).
   * Полное описание **WebSocket-протокола**: URL подключения, параметры рукопожатия/подписки и JSON-примеры всех серверных событий (`room:state_sync`, `room:player_joined`, `room:player_left`, `room:host_changed`, `room:settings_updated`, `room:player_connection_changed`).

## 6. Сборка Maven и настройка CI (GitHub Actions)

### 6.1. Запуск тестов одной командой Maven
* Все модульные и интеграционные тесты должны стабильно запускаться и проходить одной стандартной командой:
  ```bash
  mvn clean test
  ```
  (или `mvn clean verify`).
* В `pom.xml` должен быть корректно настроен `maven-surefire-plugin` (и при необходимости `maven-failsafe-plugin` + `jacoco-maven-plugin` для отчёта о покрытии кода).

### 6.2. GitHub Actions Workflow (`.github/workflows/backend-ci.yml`)
Необходимо создать рабочий CI-пайплайн, который автоматически запускается при `push` и `pull_request` в основные ветки репозитория:
1. Поднимает окружение с актуальной версией JDK (например, Java 17 / Java 21 через `actions/setup-java@v4` с кэшированием зависимостей Maven).
2. Поднимает сервис базы данных PostgreSQL (`services: postgres`) или обеспечивает работу `Testcontainers` в Docker-окружении GitHub Runner.
3. Запускает компиляцию и прогон всех тестов: `mvn -B clean verify`.
4. Публикует отчёт о прохождении тестов (Surefire reports) и падает при любой ошибке компиляции или падении хотя бы одного теста.

## 7. Критерии приёмки (Definition of Done)

* [ ] Написано максимальное количество Unit-, HTTP Integration-, Concurrency- и WebSocket-тестов, покрывающих все позитивные, негативные и граничные сценарии из раздела 3.
* [ ] **Над каждым тестовым методом присутствует подробный JavaDoc-комментарий**, описывающий проверяемый сценарий, предусловия (`Given`), действие (`When`) и ожидаемый результат (`Then`).
* [ ] Все тесты успешно запускаются и проходят одной стандартной командой Maven (`mvn clean test`).
* [ ] Все ошибки API возвращаются в едином предсказуемом JSON-формате со стандартизированными кодами ошибок (`ROOM_FULL`, `ROOM_NOT_FOUND`, `VALIDATION_ERROR` и др.).
* [ ] В `README.md` и `OpenAPI (Swagger)` подробно описаны все HTTP-эндпоинты, WebSocket-события, параметры, тела запросов и примеры ответов (достаточно для подключения FE без чтения кода сервера).
