# Задача BE-2: Реализация хранения данных, валидации игровых комнат и упаковки в Docker Compose

* **Приоритет:** Высокий
* **Тип:** Feature (Backend / Infrastructure / Database)
* **Проект:** Серверная часть многопользовательской карточной игры «Нечто» (Telegram Mini App)
* **Связь с задачами:** Расширяет и переводит на постоянное хранилище логику из задачи `BE-1` (API игровых комнат, управление лобби и WebSocket-синхронизация).

---

## 1. Контекст и цель задачи

Необходимо перевести хранение состояния игровых комнат и списка участников с объектов в оперативной памяти (in-memory) на надёжную реляционную СУБД (**PostgreSQL** или **MySQL**), чтобы состояние комнат сохранялось при перезапуске сервера.
Кроме того, требуется реализовать строгую валидацию всех входных данных, защитить подключение к комнате от состояния гонки (race conditions) при одновременном занятии последнего свободного места, исключить утечку внутренних ошибок/SQL-запросов клиенту и упаковать всё решение (приложение + БД + миграции) в единый **`docker-compose.yml`**.

---

## 2. Инфраструктура и контейнеризация (`docker-compose`)

Весь проект должен подниматься одной командой `docker compose up --build` без необходимости ручной установки СУБД или применения миграций на хост-машине.

### 2.1. Требования к `docker-compose.yml`
1. **Сервис базы данных (`db`):**
   * Образ: `postgres:16-alpine` (рекомендуется по умолчанию) или `mysql:8.0`.
   * Все параметры (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, порт) передаются исключительно через переменные окружения из файла `.env`.
   * Подключён именованный том (`named volume`, например `pgdata:/var/lib/postgresql/data`), гарантирующий сохранность данных при перезапуске контейнеров.
   * Настроен `healthcheck` (например, `pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}`), чтобы сервис бэкенда запускался только после полной готовности БД принимать соединения.
2. **Сервис приложения (`backend`):**
   * Собирается из локального `Dockerfile` (multi-stage build).
   * Зависит от `db` с условием `condition: service_healthy`.
   * Получает настройки подключения к БД (`DATABASE_URL` или `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`), порт сервера и секреты только через переменные окружения.
   * При старте контейнера (или через отдельный init-контейнер `migrations`) автоматически применяет актуальные миграции схемы к чистой или существующей базе данных перед запуском HTTP/WebSocket-сервера.
3. **Конфигурация и секреты:**
   * В репозитории должен присутствовать шаблон `.env.example` с безопасными значениями-заглушками для локальной разработки.
   * **Строго запрещено** хардкодить пароли, строки подключения к БД или секретные ключи в исходном коде проекта.

## 3. Схема базы данных и миграции

### 3.1. Сущности и связи (ER-модель)

Необходимо спроектировать и создать реляционные таблицы со связью $1:N$ (одна комната содержит от $1$ до $12$ участников) и настроить каскадное удаление или корректное управление внешними ключами.

#### Таблица `rooms` (Игровые комнаты)
| Колонка | Тип данных | Ограничения (Constraints) | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | `PRIMARY KEY` | Внутренний уникальный идентификатор комнаты |
| `code` | `VARCHAR(12)` | `NOT NULL`, `UNIQUE` | Короткий публичный код комнаты (верхний регистр, индексированное поле) |
| `name` | `VARCHAR(32)` | `NOT NULL`, `CHECK (char_length(trim(name)) BETWEEN 1 AND 32)` | Название комнаты |
| `creator_telegram_id` | `VARCHAR(64)` / `BIGINT` | `NOT NULL` | Идентификатор текущего создателя (хоста) комнаты |
| `status` | `VARCHAR(20)` | `NOT NULL`, `DEFAULT 'LOBBY'` | Статус комнаты (`LOBBY`, `IN_PROGRESS`, `FINISHED`, `ARCHIVED`) |
| `max_players` | `SMALLINT` | `NOT NULL`, `CHECK (max_players BETWEEN 4 AND 12)` | Максимальное допустимое количество игроков ($4 \le \text{max\_players} \le 12$) |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL`, `DEFAULT NOW()` | Время создания комнаты |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL`, `DEFAULT NOW()` | Время последнего обновления записи |
| `last_activity_at` | `TIMESTAMPTZ` | `NOT NULL`, `DEFAULT NOW()` | Время последней активности (для архивации неактивных комнат) |

#### Таблица `room_participants` (Участники комнаты)
| Колонка | Тип данных | Ограничения (Constraints) | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` / `BIGSERIAL` | `PRIMARY KEY` | Первичный ключ записи участника |
| `room_id` | `UUID` | `NOT NULL`, `FOREIGN KEY REFERENCES rooms(id) ON DELETE CASCADE` | Ссылка на комнату |
| `telegram_id` | `VARCHAR(64)` / `BIGINT` | `NOT NULL` | Уникальный ID игрока в Telegram |
| `username` | `VARCHAR(64)` | `NULL` | Username в Telegram (если есть) |
| `display_name` | `VARCHAR(64)` | `NOT NULL`, `CHECK (char_length(trim(display_name)) BETWEEN 1 AND 64)` | Отображаемое имя игрока в комнате |
| `is_creator` | `BOOLEAN` | `NOT NULL`, `DEFAULT FALSE` | Признак создателя комнаты |
| `connection_status` | `VARCHAR(20)` | `NOT NULL`, `DEFAULT 'ONLINE'` | Статус соединения (`ONLINE`, `DISCONNECTED`) |
| `joined_at` | `TIMESTAMPTZ` | `NOT NULL`, `DEFAULT NOW()` | Время входа в комнату (определяет очередь передачи прав хоста) |
| `disconnected_at` | `TIMESTAMPTZ` | `NULL` | Время обрыва WebSocket-соединения |

**Обязательные индексы и ограничения целостности:**
* Уникальный индекс `idx_rooms_code` по полю `rooms(code)`.
* Составное уникальное ограничение `UNIQUE (room_id, telegram_id)` в таблице `room_participants` — гарантирует на уровне СУБД невозможность дублирования одного и того же игрока в комнате при параллельных запросах.
* Индекс `idx_participants_room_joined` по полям `(room_id, joined_at ASC)` для быстрого получения списка участников и определения следующего создателя при выходе хоста.

### 3.2. Требования к миграциям
* Использовать штатный инструмент миграций выбранного стека (Prisma Migrate, TypeORM, Flyway, Liquibase, Alembic, `golang-migrate` и т.д.).
* Миграции должны храниться в системе контроля версий и накатываться на чистую БД без ручного вмешательства.

## 4. Валидация входных данных

Валидация должна выполняться на уровне входных DTO/схем до обращения к бизнес-логике и базе данных. Невалидный запрос **ни при каких условиях не должен изменять состояние комнаты** или инициировать рассылку WebSocket-событий.

### Правила валидации:
1. **Код комнаты (`code`):**
   * Обязательная строка при поиске и подключении.
   * Должна автоматически приводиться к верхнему регистру (`trim().toUpperCase()`).
   * Разрешены только латинские буквы и цифры `^[A-Z0-9]{4,12}$`. При несовпадении формата возвращать `400 Bad Request` (`INVALID_ROOM_CODE`).
2. **Имя игрока (`displayName` / `playerName`):**
   * Обязательная строка при создании комнаты и подключении к ней.
   * После удаления пробелов по краям (`trim()`) длина должна составлять от $1$ до $64$ символов.
   * Запрещены управляющие символы и неэкранированные HTML-теги (защита от XSS). При нарушении — `400 Bad Request` (`INVALID_PLAYER_NAME`).
3. **Название комнаты (`name`):**
   * Обязательная строка при создании комнаты.
   * После `trim()` длина должна быть строго от $1$ до $32$ символов.
4. **Количество участников (`maxPlayers`):**
   * Целое число (`integer`), строго в диапазоне $4 \le \text{maxPlayers} \le 12$.
   * При изменении настроек существующей комнаты новое значение `maxPlayers` не может быть меньше текущего количества уже находящихся в комнате игроков (`currentPlayersCount`). При нарушении — `400 Bad Request` (`INVALID_MAX_PLAYERS`).

## 5. Конкурентный доступ и защита от Race Conditions

### Проблема
Когда в комнате остаётся последнее свободное место (например, `max_players = 4`, а в комнате уже $3$ участника), два разных игрока могут отправить запрос `POST /api/v1/rooms/:code/join` в одну и ту же миллисекунду. Без синхронизации на уровне транзакций оба запроса прочитают `count = 3`, оба выполнят `INSERT`, и в комнате окажется $5$ игроков при лимите $4$.

### Требуемое решение (Транзакционная блокировка)
Операция подключения игрока к комнате (`joinRoom`), выхода (`leaveRoom`) и изменения лимита (`updateSettings`) должна выполняться **строго внутри транзакции БД с пессимистической блокировкой строки комнаты (`SELECT ... FOR UPDATE`)**:

1. Открыть транзакцию БД (`BEGIN`).
2. Запросить комнату с эксклюзивной блокировкой строки:
   ```sql
   SELECT * FROM rooms WHERE code = $1 FOR UPDATE;
   ```
   *(Второй параллельный запрос на вход в эту же комнату будет ожидать снятия блокировки первой транзакцией).*
3. Проверить существование комнаты (`404 Not Found`) и статус `status = 'LOBBY'` (`409 Conflict`).
4. Проверить, есть ли уже игрок с данным `telegram_id` в `room_participants` для данного `room_id`:
   * Если есть — обновить `connection_status = 'ONLINE'`, зафиксировать транзакцию (`COMMIT`) и вернуть актуальное состояние комнаты (`200 OK`).
5. Подсчитать текущее количество участников внутри транзакции:
   ```sql
   SELECT COUNT(*) FROM room_participants WHERE room_id = $1;
   ```
6. Если `current_count >= room.max_players`:
   * Откатить транзакцию (`ROLLBACK`) и вернуть ошибку `409 Conflict` с кодом `ROOM_FULL` («Комната заполнена»).
7. Если место есть (`current_count < room.max_players`):
   * Выполнить `INSERT INTO room_participants ...`.
   * Обновить `rooms.updated_at` и `rooms.last_activity_at`.
   * Зафиксировать транзакцию (`COMMIT`).
8. **Только после успешного `COMMIT`** отправить WebSocket-событие `room:player_joined` всем участникам комнаты.

## 6. Безопасность и глобальная обработка ошибок

Клиенту **категорически запрещено** возвращать:
* Сырые тексты ошибок СУБД, названия таблиц, колонок, ограничений (`constraint names`) или фрагменты SQL-запросов.
* Стектрейсы (`stack traces`) исключений.
* Значения переменных окружения, строки подключения, пути файловой системы сервера.

### Требования к Global Exception Filter / Error Middleware:
1. Все ожидаемые бизнес-ошибки и ошибки валидации преобразуются в структурированный JSON-ответ с соответствующим HTTP-кодом (`400`, `401`, `403`, `404`, `409`, `422`):
   ```json
   {
     "error": {
       "code": "VALIDATION_ERROR",
       "message": "Некорректные параметры запроса",
       "details": [
         {
           "field": "maxPlayers",
           "issue": "Количество игроков должно быть от 4 до 12"
         }
       ]
     }
   }
   ```
2. Любые непредвиденные исключения (падение соединения с БД, таймаут запроса, синтаксическая ошибка, `NullPointerException` / `TypeError` и т.д.):
   * Логируются в серверный журнал (`stderr` / логгер) с полным стектрейсом и параметрами контекста.
   * Клиенту возвращается строго обезличенный ответ со статусом `500 Internal Server Error`:
     ```json
     {
       "error": {
         "code": "INTERNAL_SERVER_ERROR",
         "message": "Внутренняя ошибка сервера. Пожалуйста, попробуйте позже."
       }
     }
     ```

## 7. Требования к интеграционному тестированию

Необходимо реализовать автоматические интеграционные тесты, работающие с реальной тестовой БД (например, поднимаемой через `docker-compose` или `Testcontainers`):

1. **Тест персистентности (сохранности данных):**
   * Создать комнату и подключить к ней игроков.
   * Пересоздать экземпляр сервиса/приложения (имитация перезапуска сервера) с подключением к той же БД.
   * Запросить комнату по коду (`GET /api/v1/rooms/:code`) и убедиться, что комната, её настройки и список участников полностью сохранились.
2. **Тест чистых миграций:**
   * Применить все миграции к пустой базе данных и убедиться в отсутствии ошибок и наличии всех таблиц, индексов и `CHECK`/`UNIQUE` ограничений.
3. **Тест на состояние гонки (Concurrency / Race Condition Test):**
   * Создать комнату с `maxPlayers = 4`, добавить в неё $3$ игроков (остаётся $1$ свободное место).
   * Одновременно (параллельно через `Promise.all` / `asyncio.gather` / пул потоков) отправить $5$ запросов на подключение от $5$ разных новых игроков.
   * **Ожидаемый результат:** ровно $1$ запрос завершается со статусом `200 OK`, остальные $4$ запроса получают `409 Conflict` (`ROOM_FULL`). В таблице `room_participants` для этой комнаты находится ровно $4$ записи.
4. **Тест атомарности при невалидных запросах:**
   * Попытаться подключить игрока с пустым именем, невалидным кодом или обновить `maxPlayers` на $15$.
   * Убедиться, что сервер вернул `400 Bad Request`, а состояние комнаты и список игроков в БД не изменились.
5. **Тест маскирования внутренних ошибок:**
   * Сымитировать ошибку уровня СУБД и проверить, что в теле HTTP-ответа отсутствуют ключевые слова `SELECT`, `INSERT`, `postgres`, `mysql`, `stack`, `at ` и названия таблиц.

* [ ] В корне проекта настроены `Dockerfile`, `docker-compose.yml` и `.env.example`; команда `docker compose up --build` поднимает СУБД, автоматически накатывает миграции и запускает сервер.
* [ ] Настройки подключения к СУБД передаются только через переменные окружения и не захардкожены в коде.
* [ ] Созданы таблицы и связи для комнат (`rooms`) и участников (`room_participants`), настроены миграции схемы БД.
* [ ] Данные комнаты и список участников сохраняются в СУБД и остаются доступны после перезапуска контейнера приложения.
* [ ] Реализована строгая валидация кода комнаты, имени игрока, названия комнаты и лимита участников ($4 \le \text{maxPlayers} \le 12$); невалидные запросы не меняют состояние БД.
* [ ] Реализована транзакционная защита от гонок (`SELECT ... FOR UPDATE`): параллельные запросы на последнее место не позволяют превысить `maxPlayers`.
* [ ] Настроен глобальный перехватчик ошибок: внутренние исключения, стектрейсы, SQL-запросы и секреты никогда не возвращаются клиенту.
* [ ] Написаны и успешно проходят интеграционные тесты для всех ключевых сценариев работы с хранилищем и конкурентных запросов.
